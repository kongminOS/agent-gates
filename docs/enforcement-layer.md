# Enforcement Layer — 把闸门从"建议"变成"权限"（方法论）

> 2026-08-24 更新。实践来源：Kongmin Rein 强制层接入生产的完整过程（CASE20/21/30/31 沉淀）。
> 本文是**方法论**：讲为什么 + 怎么设计。实现代码在闭源运行时（识海MCP/Kongmin Rein），这里只给可复用的设计模式与伪代码。

---

## 一、核心问题：提示层修复为什么必然失败

"加一条铁律让 Agent 记住"的修复方式，在我们的实战中**连续失败七次**（同一根因的不同变体）：

- Agent "以为"自己走过了闸门（专家模式/上下文压缩/记忆深厚化都会制造这种错觉）
- 判断产物只存在于 Agent 对话上下文——**机器查不到，就无法强制**
- 每次失败的诱因不同（写错目录/越权删除/专家模式绕过/记忆太强），病根相同

**结论**：闸门是"权限"不是"建议"。靠 Agent 自觉的协议，失败模式是固定的。

## 二、设计模式：闸门从"问 Agent"变成"查文件"

### 1. 状态落盘（唯一写入口）

```
gate_state/{task_id}.json
  ├── gates: { G1..G6: { passed, timestamp, ref } }
  ├── current_gate
  └── _prev_hash / _hash   ← 防篡改（见 §4）
```

- **唯一写入口**：所有闸门状态变更走同一个函数/脚本，Agent 只读。
- **G1 必须外部确认**：Agent 不能自我批准 G1（这是最容易被"自认已过"的点）。

### 2. 执行前查文件（fail-closed）

发布类操作（写正式目录/发布内容/推远端）执行前：
```
1. 取 task_id
2. 读 gate_state/{task_id}.json
3. 无 task_id / 无文件 / 对应闸门未 passed → 拒绝(422)
4. 通过 → 放行
```

**关键**：不传 task_id = 拒绝（不是放行）。曾经的后门是"不传就跳过检查"——这等于万能钥匙，必须堵死。

### 3. 人类确认通道（审批弹窗）

- 动作级审批（危险操作弹窗）= 行业标准做法（Claude Code 的 ask、MS tool-approval 同型）
- **流程级闸门**（G1-G6 阶段序列）= 市场空白（2026-08 调研：LangGraph interrupt 是唯一"结构强制"参照，但它是开发者框架不是治理产品）
- 我们的组合：**流程级状态机（结构强制）+ 动作级弹窗（人类确认）**——两层各自解决一个问题

## 三、分层：哪些能事前拦，哪些只能事后查

| 层 | 强制方式 | 说明 |
|---|---|---|
| API 端点 | 事前 fail-closed | 走 API 的发布操作，不传 task_id 直接 422 |
| 审批端点 | 事前鉴权 | 拍板端点必须 token（人类通道），Agent 无法自造"人类同意" |
| Agent 工具调用链 | ⚠️ 事后检测 | Agent 直写磁盘不经 API——**平台级 hook 才能事前拦**（Hermes 只对 shell 命令有审批，file writes 不过）；当前用哨兵（扫描正式区新文件 vs gate 记录，无关联即告警） |
| 审计记录 | hash 链防篡改 | 改记录可检出（见 §4） |

**诚实边界**：说"物理层强制全面生效"前，先确认 Agent 的实际执行路径是否经过强制点。API 层强制挡不住工具调用链——这是最常见的"纸闸门"。

## 四、审计防篡改（hash 链）

```
_hash = sha256( JSON(state 去掉 _hash 字段) + '|' + _prev_hash )
```

- 每次写入：保留 `_prev_hash`，计算新 `_hash`
- 校验：删 `_hash` 重算，不一致 = 被篡改
- **坑**：跨语言校验键序不同（Node vs Python），校验必须用与写入端相同的序列化

## 五、可复用检查清单（团队直接抄）

1. [ ] 闸门状态有磁盘落盘 + 唯一写入口
2. [ ] 发布类端点 fail-closed（不传 task_id = 拒绝）
3. [ ] G1 外部确认（人类弹窗，非 Agent 自批）
4. [ ] 审批端点带 token 鉴权
5. [ ] 审计记录 hash 链（防篡改可检出）
6. [ ] Agent 工具调用链：事前拦不了的有哨兵事后检测
7. [ ] 验收看"不相干任务 + 别的 Agent + 人不在场"能否拦住（不是看配合时走没走完）

## 附：为什么"任务顺利"不等于"强制有效"

一个真实的教训：强制层接入后第一次任务"顺利走完全部闸门"——复盘发现那靠的是**软因素**（任务契合+人在场+前科震慑），不是机器强制。Agent 随时可以自己给自己过闸门（admin 权限）。真正的合闸 = 机器真实拦下了它自己（无 task_id 被 422、G1 自批被拒）。

**验收口诀**：走完流程 ≠ 被强制。强制要"不相干任务 + 换 Agent + 人不在场"也拦得住。
