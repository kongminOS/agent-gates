# G1–G6 — Task Discipline Gates (localized, engineering-grade)

> **Status**: Production-tested in a multi-agent studio running "AI employees" for a
> one-operator business. G5–G6 added 2026-08 (adversarial review + delivery verification).
> **Position**: G1–G6 run *after* G0 (context assembly) and *before* execution. G0 answers
> "did the agent open with the right context?"; G1–G6 answer "did the agent stay disciplined
> for this task?"
> **Attribution**: The G1–G4 gate *concept* originates from
> [mattpocock/grill-me](https://github.com/mattpocock/grill-me) and the companion skills
> (`grill-me`, `to-tickets`, `to-spec`, `implement`). The G5–G6 *concept* (adversarial
> review + per-dimension delivery verification) converges in parallel with
> [PerryLink/dsh-doublecheck](https://github.com/PerryLink/dsh-doublecheck) (itself
> inspired by the same Grill-me methodology family). This repo is a **localized + hardened**
> engineering version: Chinese-first studio usage, machine-checkable gate state files,
> no-agent-self-approval rules. If you like the idea, go read the originals first.

## The six gates at a glance

| Gate | Name | Question it answers | Machine check |
|---|---|---|---|
| **G1** | grill-me | Which facts can I verify myself vs which decisions need the human? | Requires external `--confirm`; agent cannot self-approve |
| **G2** | to-spec | Is the task specified well enough to start? | `spec_ref` recorded in gate state |
| **G3** | to-tickets | Is the work broken into tickets with owners? | `ticket_ref` recorded; **required before publish-class tools** |
| **G4** | implement | Did the work land with evidence, not claims? | `evidence_ref` recorded; verify artifacts, not self-reports |
| **G5** | review | Does the delivery survive an adversarial read? | Independent read-only reviewer vs spec; `review_ref` recorded; edits after review invalidate it |
| **G6** | verify | Are the acceptance dimensions proven? | `verify_ref` + `verdict=proven` recorded; a claim without proof is refused |

Gate order is enforced by `gate_writer.py` (`gate_control/`): a task's state file tracks
`current_gate`, and only the single write entry may advance it.

## G1 — grill-me (the decision split)

Before *any* executable instruction, the agent must split:

1. **Facts I can check myself** — file system, databases, logs, prior records. These are
   never questions for the human.
2. **Decisions only the human can make** — direction, budget, launch, hiring, scope.
   These are never guessed.

Skipping G1 = a scored KPI penalty (see `docs/KPI.md`). The human does not have to
remember to enforce it — the harness and the KPI board do.

**Hardening (vs the original)**: G1 pass requires an *external* human confirmation
(`gate_writer.py pass --gate G1 --confirm`). A gate that an agent can approve for itself
is theater.

## G2 — to-spec

Turn the accepted task into a specification:

- Success criteria written down before any code/content is produced
- Acceptance tests or review checklist attached
- `spec_ref` (path/PR/URL) written into the gate state

## G3 — to-tickets

Break the spec into tickets:

- Each ticket: one deliverable, one owner, one definition of done
- Ordering and dependencies explicit
- `ticket_ref` written into the gate state

**Why G3 is the publish gate**: the technical enforcement layer
(`gate_control/tool_wrapper.py`) hard-blocks publish-class tool calls
(`publish_content`, `publish_video`, `release_dir_write`) until the task's gate state
shows G3 passed. The machine refuses, so "we forgot the gate" stops being a thing that
can happen.

## G4 — implement with evidence

- Do the work per ticket
- Close with **evidence**, not summaries: commands run, outputs returned, files landed,
  hashes/IDs where applicable
- `evidence_ref` written into the gate state

## G5 — adversarial review (2026-08)

Implementers have confirmation bias: they review their own work through the eyes that
wrote it. G5 forces an independent second read.

- **Trigger**: after G4 evidence lands. Any *new* G4 evidence after a passed G5
  **invalidates the review** (the machine resets G5 and re-review is required).
- **Reviewer**: an independent read-only reviewer (forked subagent or human). Read-only
  by default — the reviewer may not write files.
- **Basis**: the G2 spec, dimension by dimension (acceptance criteria / scope / failure
  modes), not vibes.
- **Output**: structured findings, blocker-first; `review_ref` (path to findings) written
  into the gate state, with a findings count.
- **Handling**: three enforcement intensities — `remind` (inject the critique),
  `warn` (steer one round so the model answers the findings), `block` (refuse to proceed
  until every blocker is answered).

## G6 — delivery verification (2026-08)

"Done" is a claim; G6 turns the claim into a proof.

- **Trigger**: after G5 (or when G5 has no blockers).
- **Verification**: run the acceptance checks dimension by dimension (per-dimension
  checkers, possibly in parallel), each against the G2 spec.
- **Verdict**: `proven` (every dimension passes) / `challenged` (a dimension objects) /
  `unverified` (no verification was run).
- **Gate rule**: `gate_writer.py pass --gate G6` **requires `--verdict proven`** — a
  challenged or unverified delivery is refused at the machine level. No "trust me, it's
  done" path.
- **Artifact**: a delivery report is written (spec reference / evidence timeline /
  review findings / verification results / final verdict), so the chain is traceable.

## Failure modes this kills

| Failure | How the gates kill it |
|---|---|
| Agent self-approves its own G1 | G1 hard-requires external `--confirm`; self-approval is refused (exit code 2) |
| "We skipped the gate" after publishing | Publish-class tools are machine-blocked until G3 passes |
| Agent hand-writes a "gate passed" file | Structure validation in `check_gate_passed` rejects forged/partial files |
| "I did it" with no artifact | G4 requires an evidence reference; audits are written for every call |
| "I reviewed it myself" | G5 requires an independent reviewer reference; post-review edits reset G5 |
| "Trust me, it's done" | G6 refuses any verdict other than `proven` (exit code 2) |

## Files

- `gate_control/gate_writer.py` — single write entry for gate state (init/pass/show/list;
  G5 review_ref/findings, G6 verify_ref/verdict, post-review G4 invalidation)
- `gate_control/tool_wrapper.py` — tool-call wrapper: whitelist + dangerous-op confirmation
  + fail-closed audit + gate check as step 0
- `gate_control/test_gate_guard.py` — 10 contract tests (no-state / skipped / forged /
  confirm / G5 record / G6 verdict / re-review invalidation / full chain)
- `gate_control/test_gate_evidence.py` — end-to-end skip-the-gate evidence test

## Semi-automation (2026-08 · project increment)

The gate flow can be **semi-automated** — the machine assembles, the human decides:

| Step | What the machine does | What the human does |
|---|---|---|
| Task open | Auto-generates G1's three tables (context / self-check / decision points with recommended answers) | — |
| Decision | Presents decision points with recommendations | One-click approve-all, or edit per point |
| G2–G4 | Auto-generates spec (G2), ticket list (G3), acceptance checklist (G4) | Reviews and passes |
| G5–G6 | Spins up the independent reviewer (G5) and runs per-dimension checkers (G6) | Approves the review / confirms the verdict |

Design principle: **the system carries the rigor, the human keeps the decisions** —
automation increases from G1 (human-heavy) to G6 (fully automated verification).
This is a project increment over the original mattpocock methodology; the original
remains the source of the gate *concept* (see Attribution above).
